01

系統總覽

同一套程式碼、同一個 repo，兩種資料來源。前台預設仍讀取原本的靜態 JSON 檔案；瀏覽器加上一個切換參數後，會改讀新的 Directus API。每次 push 到 main，前台跟 Directus 服務都會重新部署——不管這次改動有沒有牽涉到 Directus。

04

員工登入與網域限制的難題

lumens.com.tw 的信箱其實是用 Microsoft 365，不是 Google Workspace——MX 紀錄指向 mail.protection.outlook.com 可以證實這點。這代表沒辦法用 Google 自己的「Internal」機構限制（那只認得 Google Cloud Identity 機構內的帳號）。解法改成放在 Directus 這一層處理。

層級作用
Google OAuth 用戶端目標對象：External／測試中。任何完成登入的 Google 帳號都能通過（包含個人 Gmail）。
restrict-email-domain 擴充套件自訂 Directus 擴充套件——信箱網域不符合 ALLOWED_EMAIL_DOMAINS（lumens.com.tw），且不在 ALLOWED_EMAILS 例外名單裡的話，就拒絕建立帳號。
TS Q&A Editor 角色透過 AUTH_GOOGLE_DEFAULT_ROLE_ID 自動指派給第一次登入的帳號。可以編輯 qa_items 與手冊相關的檔案／資料夾——不是管理員權限。
踩過的坑 用 variable env 設定 Zeabur 環境變數時，是「整批覆蓋」、不是新增合併——第二次設定 Google 相關變數時，不小心把第一批的 KEY／SECRET／資料庫連線資訊全部洗掉了。之所以沒有立刻發現，是因為當時正在跑的容器還沿用記憶體裡的舊環境變數，直到下一次完整重新建置才會真的套用新設定——而那次重建剛好是一個跟 Directus 完全無關的前端改動所觸發的。以後每次都要準備一份包含全部變數的完整 .env 檔案一起套用，或改用 variable create 做新增式的修改。
